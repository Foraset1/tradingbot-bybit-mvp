# Проверка collector перед построением датасета

Collector остаётся read-only: ему не нужны API-ключи, и он не имеет торговых полномочий.
Цель soak-теста — доказать, что данные шести пар приходят непрерывно, сохраняются без
повреждений и не создают неконтролируемую нагрузку на очередь или диск.

## Порядок запуска

Сначала выполняется короткий smoke-test:

```bash
tradingbot validate-config
tradingbot collect --run-seconds 90
tradingbot audit-data
```

Девяноста секунд достаточно, чтобы проверить приём всех 36 WebSocket topics через health,
но недостаточно, чтобы получить закрытые свечи каждого интервала. Поэтому отсутствие
`kline_5` или `kline_15` в таком запуске ещё не является дефектом.

После smoke-test выполняются отдельные прогоны на один и 24 часа. Для каждого прогона
используется новый каталог, чтобы перерывы между экспериментами не выглядели как пропуски:

```bash
export TRADINGBOT_DATA_ROOT=/data/soak/one-hour
export TRADINGBOT_HEALTH_PATH=/runtime/one-hour-health.json
tradingbot collect --run-seconds 3600
tradingbot audit-data --strict --minimum-duration-seconds 2700
```

Финальный прогон:

```bash
export TRADINGBOT_DATA_ROOT=/data/soak/24-hour
export TRADINGBOT_HEALTH_PATH=/runtime/24-hour-health.json
tradingbot collect --run-seconds 86400
tradingbot audit-data --strict --minimum-duration-seconds 82800
```

В PowerShell переменные задаются как `$env:TRADINGBOT_DATA_ROOT = "..."` и
`$env:TRADINGBOT_HEALTH_PATH = "..."`.

## Что контролировать во время запуска

Health-файл должен показывать:

- подтверждённую подписку;
- сообщения каждого ожидаемого topic в текущей WebSocket-сессии;
- свежие рыночные сообщения;
- отсутствие заполнения очереди и небольшой queue high-water mark;
- допустимую задержку и синхронизированные часы сервера;
- достаточный запас диска;
- отсутствие постоянного reconnect-loop.

При штатном завершении итоговый статус должен стать `stopped`, а очередь — опустеть до нуля.
Watchdog переподключает WebSocket, если рыночный поток замолчал; disk guard останавливает сбор
до полного заполнения файловой системы.

Перед созданием обучающего датасета служба синхронизации времени должна работать. Значительно
отрицательные значения `raw_message_latency_ms.min` или предупреждения `negative_latency` в
audit report означают, что часы узла отстают от Bybit: такой прогон годится для диагностики
сборщика, но не для моделирования задержки исполнения.

## Критерии допуска к Dataset stage

Строгий audit должен завершиться с кодом `0`. Дополнительно вручную подтверждаются:

- все шесть пар присутствуют в orderbook, trades, ticker и закрытых 1/5/15m свечах;
- нет malformed JSON, неизвестных symbol/kind, пересечённого стакана и регрессии sequence
  внутри одной WebSocket-сессии;
- нет необъяснимых длинных разрывов и дубликатов закрытых свечей;
- reconnect не оставил незавершённых `.partial`-сегментов после остановки;
- прогнозируемый суточный объём подходит для retention и резервного копирования;
- версия схемы, список и SHA-256 входных файлов зафиксированы в audit report.

## Ограничение данных для maker-исполнения

Полный L50 стакан раз в секунду и все public trades подходят для первой модели направления и
результата на горизонте 5–60 минут. Они не позволяют точно восстановить положение maker-ордера
в очереди внутри секунды. Поэтому Dataset stage сначала строит рыночные метки
`TP_FIRST`, `SL_FIRST` и `TIMEOUT`. Метки `NO_FILL`, partial fill и итоговое исполнение нельзя
считать достоверными до отдельного simulator stage с более детальным потоком изменений стакана
и калибровкой по demo fills.
